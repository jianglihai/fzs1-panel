  适用设备：MIBOX-668M2 / OpenWrt 23.05 / mipsel_24kc
  本目录文件位置（上传时在这里选文件）：
      fzs1-panel\build\packages\          ← 跑过 bash build-all.sh 之后产物在这里
    （2026-10-25 起面板与引擎同仓维护，原 fzs1-openwrt-ims 固件仓库已停用）

  ★ 当前版本：imsengine 0.1.21-1  /  luci-app-fzs 0.3.7-1
    （0.1.20 / 0.3.7 修复：换卡槽/换模组后面板报「模组无响应」、短信发不出去

      详见文末「0.1.20 / 0.3.7 更新记录」）

【第 1 步】安装网页终端（LuCI 在线源）
================================================================================

  1-1  浏览器打开设备后台，进入：
           系统  →  软件包

  1-2  点上方  「更新列表…」（Update lists）
       等待进度条走完，页面会自动刷新出可用包清单。
       如果这一步报错多半是网络问题，先确认设备 WAN 已拨上号。

  1-3  在上面的  「过滤器：」输入框里输入：
            ttyd

  1-4  在筛选结果里找到  luci-app-ttyd  →  点右边的「安装…」

  1-5  弹出的确认框里会列出要同时安装的依赖包，其中有一项翻译包：
            luci-i18n-ttyd-zh-cn
       ★ 确认它在列表里（确保中文界面），然后点「安装」。

  1-6  等待安装完成。日志窗口滚动结束后出现「已完成 / 0 个错误」即成功。
       这一步会自动把 ttyd 本体和它需要的 8 个依赖库一并装好，不用单独装。

  1-7  安装完后，左侧菜单会出现：
            服务  →  终端
       点进去就是一个嵌在网页里的命令行窗口。
       也可以直接浏览器访问  http://设备IP:7681  独立使用。

  ── 到此为止，你已经可以完全脱离串口线操作后面的步骤了 ──


【第 2 步】安装 IMS 插件（本地上传两个 ipk）
================================================================================

  IMS 这两个包不在官方源里，必须走「上传软件包」。
  入口：系统  →  软件  →  「上传软件包…」→ 选择文件 → Install

  文件就在本目录（packages）下，★ 顺序不能反 ★：

    ┌────┬────────────────────────────────────────┬──────────┬────────────┐
    │ 序 │ 文件名                                 │   大小   │  sha256 尾 │
    ├────┼────────────────────────────────────────┼──────────┼────────────┤
    │ 1  │ luci-app-fzs_0.3.7-1_all.ipk           │  119 KB  │  见 sha256sums │
    │ 2  │ imsengine_0.1.21-1_mipsel_24kc.ipk     │ 1299 KB  │  见 sha256sums │
    └────┴────────────────────────────────────────┴──────────┴────────────┘

  ★ 文件名注意：面板包从 0.3.5 起带 release 号（现为 0.3.7-1）。
    浏览器如果自动加了 _1 后缀（重复下载导致），不是包坏了，随便哪一个都行。

  ★ 顺序别反：先面板、后引擎 ★
      imsengine 的安装脚本会跑 patch-fzs 处理面板文件。0.3.x 的 luci-app-fzs
      是"源码版"（fzs-at 已原生带 ims 子命令），此时 patch-fzs 会识别并跳过
      注入 —— 输出「② fzs-at 已原生带 ims 子命令（源码版），无需注入」，
      这是正常行为，不是失败。

  ★★ 0.1.12 起的一个重要变化（0.1.13 沿用）★★
      旧版引擎升级时会先把面板文件"还原"成上一次的备份。因为 luci-app-fzs
      是独立包，升级引擎不会重新解包面板，结果就是：
          opkg 里写着 luci-app-fzs 0.3.3，磁盘上的 sms.js 却是 0.3.2
          → 界面没有新按钮，看着像"功能没加进来"
      0.1.12 已修（升级时不再还原），并加了自愈：装一次引擎包，会检测面板
      文件是否缺新特征，缺了就用包内同版本副本自动补回。所以哪怕你之前已经
      被这个问题坑过，直接装新版引擎包就能恢复，不用重装面板。

  依赖不用管：
      luci-app-fzs  依赖  libc / luci-base / rpcd   （系统自带）
      imsengine     依赖  libc                       （系统自带）
      都不需要联网，离线也能装成功。

  空间提示：装之前建议先看一眼剩余空间
      df -h
      这两个包展开后约 4.3 MB，overlay 一般剩 5~8 MB，够用但不宽裕。


【第 3 步】网页终端登录，执行三条命令让服务生效
================================================================================

  3-1  打开网页终端
           方式 A：左侧菜单  服务  →  终端
           方式 B：浏览器访问  http://设备IP:7681

  3-2  登录
           用户名：root
           密  码：admin          ← 没改过就是这个默认值
       （图标ゃ命令提示符出现即可输入，输入密码时不显示字符，属正常）

  3-3  ★ 一次粘贴一行，回车，等提示符回来再粘下一行 ★
       千万不要三行一起贴，网页终端会连着灌进去，容易乱。

       ┌──────────────────────────────────────────────────────────┐
       │ 第 1 条                                                  │
       │     /etc/init.d/rpcd restart                             │
       │ 作用：重载 rpcd，让 luci-app-fzs 的 ACL 权限和菜单生效。  │
       │       不执行这条，会出现「装好了但面板没数据/菜单不出现」。│
       ├──────────────────────────────────────────────────────────┤
       │ 第 2 条                                                  │
       │     /etc/init.d/ims enable && /etc/init.d/ims restart    │
       │ 作用：IMS 注册服务加入开机自启并立即重启拉起。            │
       ├──────────────────────────────────────────────────────────┤
       │ 第 3 条                                                  │
       │     /etc/init.d/fzs-sms enable && /etc/init.d/fzs-sms restart │
       │ 作用：短信/面板后端服务自启并重启。                       │
       └──────────────────────────────────────────────────────────┘

       说明：第 2、3 条在安装时其实已经自动做过一遍，这里再执行一次是保险，
       重复执行不会有任何副作用（幂等）。

  3-4  ★ 新增（可选）第 4 条：开机读卡自愈
       ┌──────────────────────────────────────────────────────────┐
       │     /etc/init.d/fzs-simretry enable                      │
       │ 作用：让设备每次开机 30 秒后自检两块模组的读卡状态，       │
       │       读不到的自动重新初始化一次 SIM。                    │
       │ 说明：面板包安装时已自动 enable 过，这条只是核对。         │
       │       不需要跑一次（它是开机任务），不要执行 start ——      │
       │       手动 start 会真的跑一遍，约 2 分钟，且会占用 AT 口。 │
       └──────────────────────────────────────────────────────────┘
      想关掉（比如卡槽常空、或插的是不接受重试的物联卡）：
            uci set fzs-sms.globals.sim_retry=0 && uci commit fzs-sms

  ── 三条命令的实测记录（2026-10-25，设备 imsengine 0.1.13-1 / fzs 0.3.5）──
      第 1 条  /etc/init.d/rpcd restart                → exit=0
      第 2 条  /etc/init.d/ims enable / restart        → exit=0，status: running
      第 3 条  /etc/init.d/fzs-sms enable / restart    → exit=0，status: running
      执行后  fzs-at ims status → {"state":"原生 IMS 已注册（旁路）", …}
              ping 223.5.5.5   → 0% packet loss（60ms）
      即：这三条在新版上行为与旧版完全一致，不需要改写成新命令。

  ── 复测记录（2026-10-30，设备 imsengine 0.1.21-1 / fzs 0.3.7-1）──
      第 1 条  /etc/init.d/rpcd restart                → exit=0，约 1s
      第 2 条  /etc/init.d/ims enable / restart        → exit=0，约 5s（不再卡死）
      第 3 条  /etc/init.d/fzs-sms enable / restart    → exit=0，约 1s
      执行后  pidof imsengine → 16259   pidof fzs-smsd → 24243
      /etc/init.d/ims enabled     → enabled
      /etc/init.d/fzs-sms enabled → enabled
      ★ 0.1.21 特别说明：0.1.20 之前的版本第 2 条会卡住数分钟（网页终端不动、
        init.d 全部无响应）。0.1.20 修掉子 shell 抢锁，0.1.21 又修掉子 shell
        继承 fd 1000 导致锁永不释放 —— 现已实测 restart 2 秒返回、随后
        `ims running` 与 `mwan3 status` 均 1 秒内响应。若仍遇到卡住，见后面
        「出问题怎么办」里的「命令敲下去一直不返回」。

================================================================================
  出问题怎么办
================================================================================

  Q：「更新列表…」报错？
     A：设备 WAN 没联网。先在「网络 → 接口」确认 WAN 已拿到 IP。
        这一步必须成，否则第 1 步没法在线装 ttyd。
        实在装不了 ttyd，就用第 2 步的「上传软件包」方式，
        把本目录同级 ../webtty/ 里的 9 个 ipk 按序上传。

  Q：装 ttyd 提示空间不足？
     A：先删掉不用的包腾空间，或把 /tmp/luci-*</ 缓存清掉：
            rm -rf /tmp/luci-indexcache /tmp/luci-modulecache*

  Q：蜂助手菜单没出现？
     A：rpcd 没重载。执行第 3 步的第 1 条命令，然后浏览器强制刷新
        （Ctrl + F5）清掉页面缓存。

  Q：面板打开是空的 / 提示无权限？
     A：同上，rpcd 没重载导致 ACL 没生效，执行第 3 步第 1 条。

  Q：ims 状态不是 running？
     A：先看日志定位：
            logread | tail -40
        最常见是 4G 模组还没完成数据拨号，等 1~2 分钟再 restart 一次。

  Q：三条命令里第一条提示不支持 restart？
     A：换成：  /etc/init.d/rpcd reload

  Q：命令敲下去一直不返回，整个网页终端像死了一样？
     A：这是 rc.common 的 procd_lock 被某个卡住的 /etc/init.d/ims 进程占住了，
        所有 init.d 子命令都会排队（不是你的操作有错）。
        0.1.20 / 0.1.21 已修掉造成这件事的两处原因（子 shell 抢锁、子 shell 继承
        锁的 fd 1000），正常情况下不会再发生。
        万一还是遇到，开一个新的网页终端（或 SSH）敲这一条清掉：
            kill -9 $(ps w | grep 'rc.common /etc/init.d/ims' | grep -v grep | awk '{print $1}')
        然后重跑第 2 条。★ 注意：发短信、读卡、上网这些功能全部绕开了 rc.common，
        卡住期间它们照常可用 —— 不要因为 init.d 卡住就以为设备坏了。


================================================================================
  ★ 重点：IMS 注册入口在哪？为什么看起来"没带 IMS"？
================================================================================

  结论先说：**没有搞错，包是对的，但 IMS 不在你以为的地方。**

  ① IMS 的入口在「短信中心」，不是概览页，也不是独立菜单
        服务  →  蜂助手面板  →  短信中心
     进去后应该看到两张卡：上面是短信收发主卡，下面一张
     「IMS 通道」卡片（带 刷新状态 / 学习 P-CSCF 两个按钮）；
     发送目标下拉框第一项就是「IMS 通道（推荐 · 走数据通道）」且默认选中。

  ② luci-app-fzs 0.3.2 本身就是"源码版"，原生自带完整 IMS 界面
     实测核对（不是猜测）：
         sms.js 里  var MODEMS = [ { v:'ims', name:'IMS 通道…' }, … ]   ← 已存在
         sms.js 里  sel.value = 'ims'                                  ← 默认选中
         sms.js 里  imsCard / 学习 P-CSCF / ims-bridge-card 标记        ← 已存在
         /usr/libexec/fzs-at  自带 cmd_ims_status / cmd_ims_learn（995 行）
     所以 imsengine 安装时的 patch-fzs 会**全部跳过**（"源码版无需注入"），
     看起来就像"什么都没装进去" —— 这是设计如此，不是失败。
     真正的 IMS 逻辑由第二个包 imsengine 提供（/usr/bin/imsengine + /etc/init.d/ims）。

  ③ 面板会在"检测不到引擎"时主动把 IMS 入口藏起来 —— 这才是你看不到的原因
     sms.js 第 793~795 行原文：
         if (d.state === '未安装') {
             …
             if (sel.options[i].value === 'ims') sel.remove(i);   ← 删掉下拉项
         }
     即：面板每次打开都会调  fzs-at ims status，
     一旦返回  state = "未安装"，就自动把「IMS 通道」选项移除。
     所以「看不到 IMS」= 引擎没被感知到，而不是没这个功能。

  ④ 一步步定位（网页终端逐行执行）

     a. 引擎到底装上没有？（应输出 1 行 imsengine）
            opkg list-installed | grep imsengine

     b. 面板真正读的那条输出是什么 —— 这条最关键
            /usr/libexec/fzs-at ims status
        正常应该返回一串 JSON，例如 {"state":"已注册","detail":"…","imsi":"460…"}
        ★ 如果返回  "state":"未安装"  → 说明 /etc/init.d/ims 不存在
        ★ 如果返回  "state":"未启动"  → 装了但服务没跑起来
        ★ 如果返回  "state":"未注册"  → 服务在跑，但 IMS 注册还没成功

     c. 三块补丁状态（源码版时显示"源码版原生"，属正常）
            /usr/lib/imsengine/patch-fzs status

     d. 服务与状态文件
            /etc/init.d/ims status
            cat /tmp/ims_status.txt

  ⑤ 对应处理

     返回「未安装」→ imsengine 没装上，重做第 2 步上传 imsengine 那个 ipk。
        注意顺序：luci-app-fzs 必须先在。若装反了（先 imsengine），
        后装的 luci-app-fzs 会覆盖文件导致补丁丢失，补救不用重装：
            /usr/lib/imsengine/patch-fzs

     返回「未启动」→ 执行第 3 步第 2 条把它拉起来：
            /etc/init.d/ims enable && /etc/init.d/ims restart
        还不行就看日志：
            logread | tail -40

     返回「未注册」/ 卡片 ←→ 一直在"注册中"→ 需要在卡片上点「学习 P-CSCF」。
        由于本机 EC200T（模组1）固件不含 IMS 栈、读不出 P-CSCF 地址，
        标准做法是：把卡换插到模组2（EC200N）→ 点「学习 P-CSCF」让引擎
        学到地址并存盘 → 卡插回模组1，之后就直接命中，不用再逐个试候选。
        没条件换卡的，用命令行触发：
            /etc/init.d/ims learn

  ⑥ 改完设置 / 重打了补丁，浏览器一定要 Ctrl + F5 强制刷新
     LuCI 会把 sms.js 缓存住，不清缓存看到的还是旧页面（卡片像没出现）。

================================================================================
  ★ 0.1.13 / 0.3.5 更新记录（本次：SIM 读卡自愈）
================================================================================

  【背景】现场故障：某张联通卡以前能读、后来一直读不到，换别的卡又正常
      排查结论（已在设备上逐项实测）：
        AT+CPIN?   → ERROR 10        AT+QINISTAT → 0（SIM 从未初始化）
        AT+CIMI    → ERROR 13        AT+CSIM 直发 APDU → ERROR 13（无应答）
      试过 CFUN=0/1 三轮、CFUN=1,1 模组软重启、QSIMDET=1,1 强制检测，全部无效。
      同一张卡插到另一块模组立刻读到 ⇒ 卡本身没坏，是该卡座触点/压力问题，
      **软件救不回来**，只能清洁触点或卡背垫片加压。
      但这轮排查发现一个真问题，已在本版修掉（见下）。

  【根因】模组只在开机那一下初始化 SIM，之后永不重试
      EC200T / EC200N 的 AT+QSIMDET 出厂值 = 0,0，即**热插拔检测关闭**。
      于是"开机那一刻握手失败"（卡没插到底 / 触点氧化 / 上电时序）会让模组
      永久停在无卡状态：拔插卡无效、面板永远读不到卡，只能重启整机。
      —— 这正好解释了"以前能读、后来一直读不到"的观感。

  【新】开机读卡自愈  /etc/init.d/fzs-simretry（面板包自带，装完已自启）
      开机 30 秒后自检两块模组，读不到的自动重新初始化一次（最多 2 轮）。
      已经 READY 的模组完全不碰，不影响上网和收短信。
      开关：uci set fzs-sms.globals.sim_retry=0 && uci commit fzs-sms

  【新】面板概览页「重新初始化 SIM」按钮
      只在该模组读不到卡时出现，点一下让模组重新上电重读，不用重启设备。

  【修复 1】升级后新功能"凭空消失" —— opkg 显示 0.3.3，界面却是 0.3.2
      现象：装完新版面板，opkg list-installed 明明写着 luci-app-fzs 0.3.3，

                patch-fzs: 已还原 /usr/libexec/fzs-at（来自 ...orig-ims）
      修法：prerm 只在真正 remove 时还原，upgrade 时不动面板文件；
            patch-fzs 增加过期备份判断（当前文件比备份新 ⇒ 备份作废，不还原）；
            postinst 增加自愈：检测面板文件是否缺新特征，缺了用包内副本补回。

  【修复 2】点了「导出诊断日志」一直转圈 —— 面板调用 30 秒超时
      现象：按钮能点，但一直显示"正在收集诊断信息…"，最后报错。
      根因（两层）：
        a) diag 里探 AT 口用了 `fzs-atio -b 命令文件 口 输出文件`，
           而 fzs-atio 的正确用法是**命令走 stdin**（见 fzs-at 的 at_query()）：
               printf 'AT\nATE0\nAT+CPIN?\n' | fzs-atio -t 800 -d 200 /dev/ttyUSB2
           参数形式错了 ⇒ 每个口都"无响应"。
        b) 更严重：串口被引擎占着时 fzs-atio 会**永久阻塞**（实测 8 秒不返回），
           整份报告卡死。[2] 里的 watchdog 后台进程又没有重定向 stdout，
           一直攥着 rpcd 的输出管道 ⇒ rpcd 等不到 EOF，30 秒超时才报错。
      修法：按面板统一约定重写 AT 探测（stdin 传命令 + -t 800 -d 200 + flock
            共用锁），watchdog 加 `>/dev/null 2>&1`。
      验证：SSH 直跑 2 秒；**面板那条 ubus 调用 2.3 秒返回**，报告 139 行、
            12 段齐全，AT 段能读到真实数据：
                --- /dev/ttyUSB5 ---
                +CPIN: READY
                +CIREG: 1,1,15      ← 注册成功的直接证据
                +CSQ: 24,99

  【修复 3】旧 diag 卡死会留下僵尸进程，进而卡住 opkg
      现象：opkg install 报 "Could not lock /var/lock/opkg.lock"。
      根因：卡死的 diag 进程堵在 /etc/init.d/ims stop 上，opkg 拿不到锁。
      修法：即 [修复 2]；万一你之前已经中招，执行：

            （本机已清理完毕，无需再动）

================================================================================
  ★ 0.1.20 / 0.3.7 更新记录（2026-10-30，换卡槽后「模组无响应 / 发不了短信」）
================================================================================

【现象】
  把 SIM 卡从 EC200N 换到 EC200T 卡槽后：
    · 面板把模组1 显示成离线 / 「模组无响应」
    · 发短信一直转圈，发不出去
    · 以为"设备没网"（实测设备本身一直能上网，ping 30ms）

【根因】三处把串口编号写死 + 一处服务锁竞争

  1) 面板按 USB 接口 :1.4 挑 AT 口，而 :1.4 是 Quectel 的 PPP/modem 口。
     EC200T 走 PPP 拨号时 pppd 会独占它：
         pppd /dev/ttyUSB2 115200 connect chat "" AT OK ATD*99***1# CONNECT
     此时打开该口直接报 EAGAIN（"Resource temporarily unavailable"）。
     以前 EC200T 走 RNDIS 时这个口空着，所以"碰巧能用"；
     一旦切换到 PPP 就必然失败。EC200T 真正的 AT 口是 :1.3。

  2) 发短信走 /etc/init.d/ims submit，而 rc.common 执行任何子命令前都要
     先拿服务锁 procd_lock（/tmp/lock/procd_ims.lock）。启动时探测 IMS
     端口会长时间持锁，submit 就卡在 flock 上永久阻塞（实测卡 4 分钟）。

  3) init.d/ims、ims-data 里写死了 ttyUSB2 / ttyUSB4 / ttyUSB5。
     USB 每次重枚举，串口编号会整体平移（实测同一台设备不同次启动，
     EC200T 的 AT 口在 ttyUSB1 与 ttyUSB2 之间变过）。

【修复】一律改成动态发现，不再写死任何编号

  · fzs-at 新增 probe_at()：实际发一条 AT，谁能回 OK 谁才是 AT 口；
    结果缓存 60 秒（短信轮询 2 秒一次，不能每轮都探测）。
  · 新增 /usr/libexec/ims-atport：按 sysfs 的 idProduct + 接口号枚举候选口，
    :1.4 → :1.3 排序、跳过 RNDIS/DM 口；init.d/ims、ims-data 全部改用它。
  · 新增 /usr/libexec/ims-submit：发短信直接投递请求文件并等 .done，
    完全绕开 rc.common 的服务锁；init.d 的 submit 保留为它的委托入口。
  · start_bypass_watch 的后台子 shell 补上 >/dev/null 2>&1（否则攥住
    procd 管道会让 start 永不返回），且不再回调 init.d（避免自己等自己）。
  · postinst 不再同步 restart/start，改为「清理孤儿 rc.common 进程 +
    kill 旧引擎交给 procd respawn」。

【验证】（电信卡在 EC200T）
    fzs-at sim status            → 模组1 ttyUSB1 card:ok，ICCID 898603...
    fzs-at sms send 1 10000 CXLL → {"ok":true,"chunks":1}，发件箱有记录
    设备上网                      → ppp0 正常，ping 31ms

【使用上要注意】
  · 面板「重新初始化 SIM」按钮的护栏不变：正在承载默认路由的模组拒绝复位。
  · 如果发现 /etc/init.d/ims start 卡住不动（OpenWrt 框架层的服务锁竞争），
    不影响面板收发短信与读卡；清理办法：
        for p in $(ps | grep -E "rc.common /etc/init.d/ims" | grep -v grep | awk '{print $1}'); do kill -9 $p; done

================================================================================
  ★ 0.1.21 补丁（2026-10-30 19:5x，修「start 返回了但其它 init.d 全卡死」）
================================================================================

【现象】
  跑完第 3 步三条命令，表面一切正常（start/restart 都返回了），
  但接下来：
    · 再敲 /etc/init.d/ims running      → 永远不动
    · 敲 /etc/init.d/mwan3 status        → 一样不动
    · 网页终端像死了，面板里 init.d 相关操作全无响应
    · 更糟：升级装包时 opkg 卡在 prerm 的 ims stop 上，一半装完

【根因（真机用 /proc/<pid>/fd 定位）】
  卡住的是 start_bypass_watch 派出的后台守望子 shell。
  它的 cmdline 与父进程一模一样（也是 "/bin/sh /etc/rc.common /etc/init.d/ims start"），
  所以 ps 里看起来像 start 没退出 —— 其实是那个子 shell 还活着，且：

      /proc/<子shell pid>/fd/1000 -> /tmp/lock/procd_ims.lock

  也就是说它**继承了 rc.common 的锁文件描述符**。flock 的锁归属于「打开文件描述」，
  父 shell 退出并不会释放，只要还有任何进程攥着这个 fd，锁就一直被占。
  于是后续每条 init.d 子命令都排在 flock 上等死（mwan3 status 也被殃及，
  因为它是同一把 procd_lock）。

  为什么 0.1.20 没修掉：0.1.20 只解决了「子 shell 吊住 procd 管道」和
  「子 shell 去抢父进程的锁」两件事，没意识到**继承 fd 等于一直持锁**。

【修法（一行重定向）】
      } 1000>&- 9>&- >/dev/null 2>&1 &

  在子 shell 里把 fd 1000 关掉 → 锁随最后一个引用消失而释放。
  守望进程本身照常跑（该切旁路还是会切），只是不再攥着锁。

【验证（0.1.21，实测）】
  /etc/init.d/ims start     → 4s 返回
  /etc/init.d/ims restart   → 2s 返回
  /etc/init.d/ims running   → 1s（此前必卡死）
  /etc/init.d/mwan3 status  → 1s（此前必卡死）
  /proc/*/fd 里已无进程持有 procd_ims.lock
  ims status → {"state":"已注册","detail":"ims 注册成功",…}
  sms send   → {"ok":true,"chunks":1}

  已经装 0.1.20 的用户建议升到 0.1.21；只装 0.1.20 也能用（短信/上网/读卡都正常），
  但每次跑 init.d 有可能把锁留在后台，久了会累积，表现为"面板越用越卡"。
  升级命令：opkg install imsengine_0.1.21-1_mipsel_24kc.ipk
